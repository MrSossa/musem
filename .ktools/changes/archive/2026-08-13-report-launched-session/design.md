# Technical design — report-launched-session

## Technical context

Everything here lands in the view. The launch path itself is unchanged: it
already produces a `musem.LaunchOutcome` carrying the session id, the substrate
name, the directory, the branch and the worktree — every field the report needs
is already in it.

```
musem.go / launch.go       domain: LaunchOutcome, already sufficient
internal/tui/
├── launch.go              the form; LaunchedMsg closes it and says nothing
└── tui.go                 renderHeader, and renderKept beside which this draws
.ktools/specs/session-launch/spec.md   R25 corrected
```

Two things in the existing code shape the decisions below.

`renderKept` in `tui.go` is the precedent: worktrees kept when their session
ended are announced in the header, clipped to the terminal width, bounded to two
lines with the rest counted. It exists for the same reason as this — something
happened that has no row to sit beside — and this should look like it rather than
inventing a second idiom.

The header's line budget is load-bearing. `View` charges the header by counting
its newlines and gives the table what is left, so a line long enough to wrap
occupies a row nobody budgeted for and pushes the fleet total off the screen.
Every line added here is subject to that.

## Decisions

### D1 · The report is the view's own state, not the domain's

**Chosen**: the model keeps the outcomes of launches it has made and has not yet
seen arrive. `LaunchedMsg` already carries the outcome into `Update`; it is
stored there instead of being dropped.

**Rejected alternatives**: carrying it the way kept-worktree notices travel —
held by the launcher, joined in by `app`, read off the snapshot. That route
exists because reclamation happens on the registry's schedule, with nobody
watching, so the only place to put the result is somewhere the view can later
read. A launch is different: the view started it and the view is told when it
finished. Sending that fact down through two packages to have it handed back is
ceremony, and it would put a piece of interface state in a package that has no
interface in it.

**Consequences**: the report does not survive musem being closed, which is
correct — it is a statement about what just happened in this session of the
program, not a fact about the machine. It also means no change to `app` or
`launch` at all, so this change cannot break reclamation.

**Requirements it supports**: R32, R33

### D2 · It clears by looking for the session, not by waiting

**Chosen**: on every snapshot, a reported launch whose session id appears among
the rows is dropped. No timer.

**Rejected alternatives**: expiring after a fixed interval. That is the version
that breaks precisely when the report matters: an agent waiting on a confirmation
can sit there for as long as the user is away, and a notice that expired on a
timer would take the only clue about it off the screen while the situation it
describes is still true. Also rejected: clearing on the first snapshot after the
launch, which would be a report nobody could read.

**Consequences**: a session that never appears keeps its line indefinitely. That
is the intended reading rather than a leak — a launch that never showed up is the
case the user most needs telling about. The number on screen is bounded by D3,
so several of them cost a fixed amount of space.

**Requirements it supports**: R33

### D3 · Drawn in the header, under the rules already in force there

**Chosen**: the report lines go in `renderHeader`, beside the kept-worktree
notices, clipped to the terminal width with `clip`/`padWide`, bounded to two with
the remainder counted on one more line.

**Rejected alternatives**: keeping the form open on a success pane. It puts the
information behind a pane the user has to dismiss, and it stops the dashboard
being visible at the moment the user most wants to watch a session appear on it.
Also rejected: a row in the table for a session that does not exist yet — the
table is the inventory, and inventing rows in it would make the one thing on
screen that is supposed to be observed reality partly imagined.

**Consequences**: two more lines at most in a header that already has five
possible ones, on a dashboard whose narrow-terminal behaviour is specified. The
narrow-terminal tests cover it because they cover the header, not because
anything new was added to them.

**Requirements it supports**: R32, R33

## Impact

| Area | Impact |
| --- | --- |
| Data schema | None. Nothing is persisted; the report lives as long as the process |
| Public API | None. musem is a binary and the CLI gains no flag |
| Security | None. Nothing new is created, removed or written. The report names a tmux session and a path that are already the user's, and the tmux name is generated by musem rather than being foreign text |
| Performance | Nothing added to the refresh path beyond a lookup of a handful of session ids against the rows already in hand |
| Dependencies | None |

## Test plan

- **View tests** (`internal/tui`): the report appears after a successful launch
  and names the substrate, the directory, the branch and the attach command; the
  worktree-off case names no worktree; a failed launch reports nothing as
  started; the report survives snapshots that do not contain the session and says
  so; it is withdrawn by the first snapshot that does contain it; several
  reported launches are bounded and counted. All of these drive the model with
  `LaunchedMsg` and `SnapshotMsg`, which is how every other view behaviour here
  is tested.
- **Narrow terminal** (`internal/tui`): the report is subject to the same width
  discipline as the rest of the header, under the existing tests for it.
- **Living spec**: R25's correction is a documentation change and is verified by
  reading, not by a test. The behaviour it now describes — an agent that waits to
  be let in and is then observed under the launch's identifier — was established
  by hand on 2026-08-13 and is recorded in the proposal; it is not reachable from
  an automated test without a real agent tool and a real confirmation.
